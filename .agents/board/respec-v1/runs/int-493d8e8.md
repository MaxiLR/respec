## Findings (cross-ticket, non-blocking)

1. `layer off` on an active profile does not relink. A conflict leaves the
   hand-enabled skills (d2) enabled but unlinked. `layer off` resolves the
   conflict and reports success with `"active": true, "linked": []`, but
   d2 stays out of the target folders until the next `use` (reproduced in
   `smoke4.log`, where `use work` then installed d2). `status` does not show
   the gap. `set_active`'s docstring ("no skill changes state, so the target
   folders are not touched") does not hold for this case. Fix with a refresh
   on turning off, or leave it for the 011 Sync "missing managed installs"
   check.
2. A refused layer change says "switch": `layer disable` on a conflicted
   active profile, or any layer change that is blocked by unknown entries,
   prints `cannot switch to profile 'work'`. The refresh calls
   `switch.use`'s default action text, even though `refuse_layer_conflicts`
   accepts an `action` argument. The output is only misleading, since
   "Profile 'work' was left unchanged." follows.
3. Unrelated unknown entries block `layer repair` on the active profile:
   `layer repair --keep d2` failed with the unknown `stray` error. The
   rollback was correct. This is the existing refresh-blocks-on-unknown
   model, which fix-6 is reworking.
4. Already present on base `f629644` (verified there): entries that exist
   at first takeover show up as `unknown folder` even after
   `use --unknown keep`, and they then block every refreshing command until
   `adopt`. This is in fix-6's scope ("ask about pre-existing entries at
   first takeover").
5. Dead code `exclusivity_problems()`, the `add_skill` duplication of
   `enabled_members()`, and internal "item" naming (see above).

No blocking integration failures. fix-5 composes with 001-010, fix-1 to
