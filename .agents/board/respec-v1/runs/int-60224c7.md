## F1: copy-mode item replaced by another tool is deleted without backup

**Confirmed at 60224c7.**

Reproduction: a scratch pytest file using the project conftest (temp homes),
kept outside the repo at
`/private/tmp/claude-501/-Users-maxilr/5b61f2f4-75a0-4c28-a72a-0a819912c26c/scratchpad/f1/test_f1_repro.py`.

1. Profile `a` (claude-code, `tdd`) and profile `b` (claude-code, `lint`).
2. `respec use a` with `os.symlink` refusing, so `tdd` is installed in copy
   mode. state.json records `mode: copy`.
3. Another tool replaces `~/.claude/skills/tdd` with its own folder whose
   SKILL.md says `FOREIGN TOOL CONTENT`.
4. `respec status --json` lists `tdd` under `items` as a managed `copy`. The
   folder's `unknown` list is empty.
5. `respec use b` exits 0 with `Removed 1 items of profile 'a'`. The foreign
   folder is gone, and no backup holds its content (`backups: []`).

Root cause:

- `unknown.is_managed` checks only `os.path.lexists(path)` for `mode == "copy"`.
  The replacement therefore never counts as unknown, never gets `replaced`, and
  never triggers the prompt.
- `switch._remove` then runs `shutil.rmtree` on any existing recorded copy-mode
  path.
- The unknown.py docstring states the limitation ("a recorded copy must still
  exist"), but no ticket or spec text accepts it.

**Spec violation: yes.** It breaks the user story "when another tool drops a
skill into a folder respec owns, I am offered to adopt it, back it up and
remove it, or keep it unmanaged, and nothing is silently lost". It also breaks
decision 5, which says unknown entries are listed before a switch and in
`status`. Copy mode is only a fallback for when symlinks fail (a proposed
default), so this is rare on macOS and Linux. It is still silent data loss when
it happens. The fix needs some identity for a copy, such as a content
fingerprint or marker recorded at install time.

## Cross-ticket contract review

### Works together (no issue)

- **002 switch engine.** Step 0 (`UnknownEntries`, a `SwitchBlocked` subclass)
  runs before preflight, takeover and removal. When it refuses, nothing has
  changed. `_forget_replaced` and reloading the profile after `on_unknown`
  handle an `add` into the profile being activated. When a replaced symlink
  blocks the switch, the CLI now explains it clearly, not the generic
  preflight "already exists" error.
- **006 items.** `add_local(name=...)` is backward compatible and keeps the
  entry's own name for symlinked entries. `items._refresh` catches
  `SwitchBlocked`, which now includes `UnknownEntries`, and rolls the profile
  edit back. Tests cover this (`test_item_change_is_rolled_back_when_replaced_link_blocks_refresh`).
- **008 layers.** `layers._apply` goes through `items.commit`/`_refresh`, so it
  rolls back the same way (`test_layer_change_is_rolled_back_while_an_unknown_entry_waits`).
- **state.json.** `unmanaged` is optional on load, validated, and always
  written. Older files still load.
- **status.** Items of targets that share one real folder are listed once,
  under the first target, with `same_as` for the aliases. Replaced items are
  left out of `items` and shown as unknown.

### Findings (none block the merge)

1. **F1 (above).** Copy-mode replacement is not detected and is deleted on the
   next switch. It violates the spec user story and decision 5.
2. **Duplicate helper.** `switch._real` (switch.py:96) is identical to
   `unknown.real` (unknown.py:44), docstring included. `switch.py` already
   imports `unknown` and uses `unknown.real` in `_forget_replaced`, so the
   module uses both.
3. **Duplicate ordering logic.** The owned-target sort by registry order
   appears twice: in `switch.status` (switch.py:307–310) and in
   `unknown.folder_groups` (unknown.py:62–66).
4. **Private cross-module use.** `adopt.py` imports `switch._utc_now` and
   `switch._new_backup_run`. Both are now a shared contract between modules
   and should be public, or should live in a shared module.
5. **Effectively dead branch.** In `switch._remove`, the branch
   `if item.mode != "copy": return False` ("a recorded symlink was replaced")
   can no longer be reached through `use()`. A replaced symlink is now
   unknown, so the switch either refuses before removal or `_forget_replaced`
   drops the record first.
6. **Misleading hint on item and layer edits.** When an unknown entry exists
   in an owned folder, `add`, `remove`, `enable`, `disable` and `layer …` on
   the active profile are refused. This happens even when the entry has
   nothing to do with the item being edited. The error comes from
   `UnknownEntries` and reads "cannot switch to profile …" followed by "pass
   '--unknown add|backup|keep' to 'respec use'". Those commands have no
   `--unknown` option and the user did not ask to switch. The behaviour
   itself is tested and intended. Only the wording is off.
7. **Stale `unmanaged` paths.** `state.unmanaged` is never pruned. If a kept
   entry is deleted and a different entry later appears at the same path, it
   is silently treated as kept and never reported. Nothing is lost, but
   detection is missed. Minor.

### Vocabulary against the spec

The code uses the spec's terms: "unknown entries", "owned folder", "add to
profile / back up and remove / keep unmanaged", `respec adopt`, and
`backups/<timestamp>/<target>/`. There is no drift. The README section matches
the behaviour, apart from the claim "Nothing is removed before it is copied
into a profile or a backup", which is false for F1.
