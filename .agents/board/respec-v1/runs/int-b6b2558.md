- `grep -rn -- '--home' src tests README.md` finds matches only in
  `tests/test_profile_list_show.py:146-155`. That test asserts that `--home` is
  rejected in the root, subcommand and `tui` positions. There are no matches in

- The real entry point rejects it: running
  `HOME=<tmp>/h1 .venv/bin/respec --home <tmp>/h2 profile list` exits with

  parameters. `cli.main` builds `Homes` from environment variables only.

  and `RESPEC_HOME` as advanced/testing environment overrides. The spec (line 108) requires only "an overridable home", so it is still satisfied.

## Earlier cross-ticket finding (first-takeover backup skipped)

These scenarios used the real binary on scratch homes.

- **No `RESPEC_HOME`, switching `RESPEC_USER_HOME`/`HOME` from h1 to h2:**
  each home gets its own `.respec`. Both runs printed
  `Backed up agents folder to .../hN/.respec/backups/<ts>/agents`, so the
  backup is no longer skipped. With no CLI option left, the original path
  through `--home` cannot be triggered.
- **Residual path, environment variables only (low severity):** with
  `RESPEC_HOME` fixed at a shared folder and `RESPEC_USER_HOME` switched from
  u1 to u2:
  1. `use q` in u1 backs up the u1 agents folder.
  2. `use q` in u2 is first blocked by the unknown entry `u1/.agents/skills/a1`.
     The block refers to the old home, not the current one.
  3. Running `use q --unknown keep` in u2 installs into `u2/.agents/skills`
     **without backing up u2**. In `state.json`, `owned.agents.skills_dir`
     still points to u1. The existing entry `u2/.../b1` is never classified as
     unknown.

  The cause is unchanged: `state.owned` is keyed only by target name and is not
  revalidated against the resolved `skills_dir` (`switch._take_over`, the
  `new_targets` filter). The only way to reach this is now the combination of
  two advanced/testing environment variables, which the engineer decided to
  keep. I consider it not blocking. It is noted for the engineer in case
  `owned` should also be keyed or checked by `skills_dir`.
