## Contract review: 008 against 006's enable/disable and switch engine

- 008 routes layer changes through `items.commit`, which saves the profile, then
  `_refresh` re-runs `switch.use` and undoes the change on `SwitchBlocked`. This is
  the same engine path 006 uses. The switch engine does not read layers; it reads
  only `SkillEntry.enabled`. This matches the spec: "layers never change install
  locations".
- `parse_profile` rejects hand-edited profiles that break the exclusivity rule.
  `use` and `status` then fail on load with a list of the problems, so the switch
  never installs an inconsistent profile.

## Findings (cross-ticket)

1. **Medium: `enable` hides an item it disables as a side effect.**
   `items.set_enabled` now calls `profiles.with_enabled`. In an active exclusive
   layer, this quietly disables the previous choice. Neither the `ItemChange` JSON
   nor the text output names the disabled item.
   - For an active profile, the only sign is a path in `unlinked`.
   - For an inactive profile, there is no sign at all. Probe: profile q,
     `enable b -p q --json` returned `"linked": [], "unlinked": []`, but
     `layer list` then showed `a (disabled)`.
   - Agents using `--json` cannot see this state change. A field such as
     `disabled: [...]` (or similar) is missing from both `ItemChange` and
     `LayerChange`. `layer use` has the same gap.
2. **Low: duplicate helpers in `cli.py`.** `_layer_item_command` (line 491) and
   `_layer_flag_command` (line 536) have identical bodies.
3. **Low: type drift.** `items.commit` and `items._refresh` declare
   `change: ItemChange` but also receive `layers.LayerChange`. The docstring admits
   duck typing. A small Protocol, or a shared base, would make the contract
   explicit. `layers.describe` and `layers.remove` have no return annotations.
4. **Low: empty layer description accepted.** `layer add x --additive -d ""`
   succeeds. `--description` is labelled "(required)", and spec decision 10 says the
   description explains what belongs. The parser checks only that the key is
   present and is a string.
5. **Low: `profile show` ignores layers.** The text and `--json` output from ticket
   002 do not include layers (`layers` count in the JSON: 0). Layers are visible
   only through `layer list` and `layer show`.
6. **Info: spec vocabulary.** The spec says "with layers off, a profile is a flat
   additive list". The implementation has only per-layer `on`/`off` (JSON `active`)
   and no profile-wide switch. A profile is flat only after every layer is turned
   off. This is a reasonable reading of the spec, but the difference is unrecorded.
   Existing terminology mixes "Skills:" (`profile show`) and "items" (layers). This
   predates 008.

No dead code found apart from the duplicate helper in finding 2.
`items.remove` strips layer membership inline instead of using a `profiles`
helper. This is acceptable and has a single use.
