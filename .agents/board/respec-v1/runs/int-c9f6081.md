## Cross-ticket findings (none blocking)

1. **The TUI's interrupted-change banner goes stale.** This is TUI and 003,
   reproduced in both rounds.
   - After Sync finishes or rolls back the change and closes,
     `RespecApp.refresh_view` runs: the active line updates to
     `● Active pi`/`work`.
   - But `#feedback` still reads "An interrupted change waits … Until then
     respec changes nothing else."
   - The cause: `refresh_view` only sets this feedback while a journal is
     pending. It never clears it once the journal is gone.
2. **`status` lists respec's own in-flight link as an unknown entry while a
   switch journal waits.**
   - After the kill at `installed #2`, `rev` (the `pending` install step's
     link) showed as `rev  unknown symlink`. The text ends with "Resolve them
     with 'respec adopt'".
   - `status --json` lists `rev` under `unresolved` (`json.35`).
   - No harm results, because `adopt` recovers first. Still, the
     `unresolved` contract and the advice are wrong for that entry.
3. **Documentation and contract drift for the new warnings.**
   - `shipped/respec/SKILL.md:20` lists the warning types as
     "`layer-conflict` or `interrupted-operation`". It is missing
     `unreadable-manifest`, which README:314 documents and
     `cli._print_json` emits.
   - The `cli._print_json` docstring also leaves out `unreadable-manifest`,
     and leaves out `outcome` `rebuilt` and `operation` `state`.
   - README (the `error` bullet) says that commands other than `use`, `adopt`
     and `restore` "print their error on stderr only". But `recover --json`
     prints a JSON object with `active_profile`, `recovered: false` and
     `error`, and so does `restore --release-only` (a restore variant).
4. **Duplicate helpers and dead code.**
   - These three helpers have identical "active profile from state, or None
     on RespecError" bodies:
     - `cli._SwitchRun._active` (cli.py:477);
     - `cli._active_or_none` (cli.py:708);
     - `tui.RespecApp._active_now` (tui.py:1592).
   - In `journal.describe`, the first mapping (`restore`/`adopt`) repeats
     entries of the second.
   - `journal.OPERATIONS` is never used (vulture).
5. **A rerun of an interrupted restore reports empty result lists.**
   `restore --json` after the kill returned `released: []`, `restored: {}`
   and `removed: []`, although it released all three folders. Only the
   `interrupted-operation` warning (`finished`) says what happened.
6. **Wording.** For an unknown or malformed journal the message reads "An
   interrupted 'bogus' change (started an earlier run) was interrupted and did
   not complete." It doubles "interrupted", and "started an earlier run" is
   ungrammatical.

Note only:

- After `recover` rebuilds `state.json`, the former profile's links stay in
  place with no profile active. `consistent.py` flags 3 folders.
- This is documented ("No profile is active: run 'respec use <profile>'"),
  and a bare `restore` still works byte-identically afterwards.
